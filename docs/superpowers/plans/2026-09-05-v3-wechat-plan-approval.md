# 第三版：微信同意计划审批实施计划

## 范围和当前结论

本版只做用户通过微信 ClawBot 明确同意后，批准唯一绑定的 Agent、session、当前待审批计划并启动执行；不加入其他通知或刷新功能。不修改 ZCode 本体，不竞争已有消息消费者，不恢复失败自动重发。

状态：已完成原生接口门禁调查，实装受阻。第二版已经提供 `awaiting_approval`、来源/会话/回合关联和可选计划指纹，但这些是通知事实，不是受权控制入口或原生交互 ID。不得仅凭通知记录把任意“同意”转为桌面指令。

## Task 1：受控接口门禁（已调查，未通过）

写集：本计划及 `docs/native-control-capabilities.md`；应用包与用户运行数据只读。

已确认 ZCode 原生 `pendingElicitation` 经 `respondElicitation` 和 `resolveInteraction` 处理计划批准；`/approve` 只处理权限请求。机器人 watcher 自己保存的 pending 可以由同一 actor 回复“批准”，但 `/task` 不导入桌面已有 pending，未确认“同意”别名，也没有有效期校验。未确认独立公开 HTTP/IPC 审批入口；Web Remote 的配对桥接不能当作可任意调用的 API。

缺失的必要能力：

1. 在模型对话前安全识别并消费控制词的原生扩展点，且不争抢机器人消息队列。
2. 经显式配对/授权、能读取和解决指定 Agent 桌面会话当前交互的稳定入口；ZCode 和 Codex 必须分别有实证适配。
3. 可验证的发送者、消息 ID、原生交互 ID 和当前计划版本，支持有效期及单次消费。

继续实装需要新增受控原生扩展能力，或另行明确授权的独立配对控制链路。不得读取其他会话的配对凭据、注入应用、模拟点击或将新对话提示冒充原生批准。本轮没有安装远程控制服务或自动审批任何真实任务。

## Task 2：最小审批账本和授权绑定（依赖 Task 1，未实施）

预期写集：独立审批模型、持久化存储及合成测试；不改当前通知状态的授权语义。

采用一次性审批标识，绑定已授权 sender、agent、session、turn、interaction 和计划指纹。明确有效期，以事务持久化 pending/consumed 状态；仅 `awaiting_approval` 可进入批准流程。计划变化、取消、过期、已恢复、缺少唯一匹配均拒绝，不能默认选择最新任务。

先验证错误用户、多候选、指纹变化、超时、重启、重复消息与并发批准，再接线；日志只保留脱敏关联与状态，不记计划正文、凭据或 token。

## Task 3：控制消息和来源审批接线（依赖 Task 2，未实施）

预期写集：受控入站适配器、ZCode/Codex 审批适配器、配置及测试。入口必须在普通对话前精确匹配，不以聊天正文包含“同意”触发。成功原子消费，调用明确原生交互，不重跑任务或发送通用“开始做”代替批准。

超时或结果不明确时进入待核查状态，不自动重发。仅提供经过验证的来源适配器；其他来源拒绝，不把扩展占位当成已支持。

## Task 4：端到端验收与发布（依赖 Task 3，未实施）

用隔离测试会话验证：微信精确批准只启动正确的一项计划；相同消息重复、双击、重放、过期、错误账号、旧计划、已完成任务都不启动；普通聊天不受影响。模拟控制入口失败和回复超时，确认没有第二次启动。静态/合成通过不能代替真实微信到达及桌面交互验证。

实现完成后独立审查、隐私与全套回归、白名单中文提交、立即推送并核对远端。未通过 Task 1 前不提供会误导用户的安装开关、示例审批命令或“已支持”文案。

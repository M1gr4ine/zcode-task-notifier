# 第二版：实际停顿通知与外置控制实施计划

> 2026-09-05 需求修订：下文 Task 3 的旧归属账本与“按来源十条”方案已被用户替换。当前规则为通知工作区内“自动化关联 + Agent 标签”，所有来源合计保留最新五条，具体保护与恢复边界以 README 为准。下文旧执行记录保留用于追溯，不代表当前清理实现。

依据：`ROADMAP.md`，以及用户补充“只通知每次真正停下来需要用户处理、彻底完成或失败；规则确认不通知”。第一版已发布，第二版按以下任务顺序逐项提交并推送。

## 目标与架构

继续采用 Python 外部只读扫描器、持久化事件去重、ZCode 单次 GLM 自动化及原微信投递链路。来源适配器负责识别事实，公共停顿策略负责分类，通知层只展示已判定的状态，不让摘要模型裁决是否需要通知。公开代码不得包含本机路径和真实数据。

## 全局约束

- 不修改 ZCode 本体；不重新引入失败自动重发；仅用户手动触发安装技能。
- 初始化/规则确认/就绪/等待第一项任务/普通进度不通知。
- 只通知实际任务的计划待审批、待用户选择、完成、失败。待选择与待审批不能混同，后续只有明确待审批才可审批。
- 现有基线、增量游标、单实例锁、全工作区扫描和幂等键必须保留；新字段向后兼容。
- 每个功能完成、测试、独立审查后白名单提交并立即推送，核对远端 SHA。现有隔离发布目录继续使用；已获授权推送 main。
- 原版接口调查是实施门槛；没有受控入口不假装实现，不劫持已有微信长轮询、不修改应用文件、不把轮询抢到消息当可靠控制功能。

## Task 1：停顿识别及状态

写集：`models.py`、`state.py`、`codex_source.py`、`zcode_source.py`、新 `stop_policy.py`、`notifier.py`（仅状态文案）、`service.py`（等待首发前复核）、必要测试、README。

接口：Event.status 兼容 completed/error，新增 awaiting_approval/awaiting_input；增加可选 stop_reason、稳定计划摘要指纹（如有），不持久化完整用户输入。来源保留 agent/session/turn 关联。分类函数返回可通知状态或忽略原因。

步骤：
1. 先写失败测试：截图等价规则确认忽略；实际任务完成保留；计划明确等待批准与方案选择分开；普通进度/仍在运行忽略；失败保留。
2. 从真实记录结构提取本回合用户任务证据，排除系统上下文/AGENTS/环境/插件列表。只有规则输入时不可作为真实任务。未知旧格式保留明确最终结果兼容，但不能仅凭 task_complete 通过。
3. 结合结构化终止/等待与最终文本分类；不要因正文引用“失败/同意/计划”等词误判。结构化等待只在尚未恢复时通知；不把非阻塞异步问题当停顿。
4. 对增量跨轮扫描保存最小上下文，避免丢失输入依据；历史补全不能绕过过滤；被忽略事件推进游标/去重，避免后续反复出现。
5. 通知提示词固定真实状态及时间语义；待审批/待选择不能写成完成；旧状态文件可读。
6. 测试覆盖同 session 后续任务、跨扫描输入/结束、历史降级、基线不洪泛、空回复/仅进度、引用与否定、结构化停顿及恢复。

验证：对应 source/state/notifier/service 测试和新增停顿测试，完整 pytest，隐私扫描；本地部署仅更新外置 app，保留 config/state 和隐藏计划任务。

可观测性边界：本版识别已落盘的实际最终回复、明确等待文本和 Codex 阻塞交互事件。ZCode 原生仍显示 running、且审批/选择只存在应用内存而未落盘的交互，不在只读外置脚本的可观测范围；不得用 running 正文关键词推断停顿，也不得宣称已经覆盖这类原生弹窗。后续需官方受控事件入口才能补全。

## Task 4：仅刷新微信上下文的控制指令

先只读调查原版微信收消息路径、context_token 更新顺序、命令短路能力、可扩展接口。若原生支持直接复用并记录使用方法。若没有，只有外部受控接口可完整满足不触发对话时才实现：精确匹配 `/刷新`，权限绑定、重复/并发/失败处理、无模型调用或新会话，非控制消息行为不变。不得通过删除已生成任务冒充不触发对话，也不得竞争同一 bot 消息队列。无安全入口时记录具体证据和阻塞，不修改本体。

## 后续第三版

第二版收尾后建立独立审批计划，只做微信明确同意到唯一待审批计划的安全启动。复用本版来源/session/turn/计划指纹；鉴权、有效期、防重放、幂等、防误批和审计作为前置条件。不能因通知启用就默认授权任意聊天启动本机代码。
